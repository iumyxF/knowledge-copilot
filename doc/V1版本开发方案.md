# Knowledge Copilot V1 版本开发方案

状态：已按确认范围完成编码与工程验收；真实模型质量验收待配置。实施与验证记录见 [V1编码任务清单](./V1编码任务清单.md)。

依据：[应用开发计划](./应用开发计划.md)、项目 AGENTS.md，以及本次 grill-me 访谈已确认的范围。本文细化 V1，未列入本版的能力继续遵循原计划的后续版本安排。

## 1. 交付目标与已确认范围

V1 交付一个可通过 Knife4j 调试和验收的 Java 后端，完成“上传文档 → 异步入库 → 单轮问答 → 返回引用 → 运行检索评测”的闭环。

| 项目 | V1 决策 |
| --- | --- |
| 工程目录 | 根目录下 `server/` 存放后端；`web/` 预留前端，仅放 `.gitkeep` |
| 前端 | 不开发 Vue、HTML 页面或其他前端业务代码；使用 Knife4j 自带界面 |
| 认证 | 不做登录、用户、角色、权限和多租户 |
| 知识库 | 支持多个知识库，请求明确指定 knowledgeBaseId |
| 文档 | 上传、列表、详情、状态查询、切片查看、失败重试、删除 |
| 文件 | PDF、DOC、DOCX、TXT、Markdown；单文件默认 20 MB，可配置 |
| 解析 | PDF 只处理可提取文本的文件；不做 OCR，无有效文本时明确失败 |
| 入库 | 应用内有界线程池异步处理，MySQL 保存状态，无消息队列 |
| 问答 | 单轮、非流式，一次返回答案和引用；不保存会话与聊天历史 |
| 拒答 | 没有检索结果时直接返回固定拒答，不调用对话模型 |
| 模型 | 用户后续配置服务商、地址、模型名、密钥及向量维度 |
| 评测 | 文档级 Recall@5、Recall@10、MRR@10、Hit Rate@10 |
| 基线 | 随项目提供中文示例文档、评测集和导入说明 |
| 验收 | 流程可用、指标计算正确、结果可追溯；不预设真实业务召回率门槛 |

不进入 V1：文档内容替换、已成功文档重新切片、人工 Split/Merge、ChunkSet 发布与回滚、Hybrid、BM25、Query Rewrite、Reranker、ChatMemory、完整 Trace、Feedback、LLM Judge、Agent、MCP。

后文未在访谈中逐项指定的参数属于本方案默认值，可在实施时按实测调整并记录，不改变上述交付范围。

## 2. 架构与工程组织

采用 Java 21、Spring Boot 3.5.x、Maven、MyBatis-Plus、MySQL 8、Elasticsearch、LangChain4j 和本地文件系统。单实例、模块化单体、一个 Maven 应用，不提前拆多模块工程。

```text
Knife4j / HTTP Client
          ↓
Spring MVC Controller
          ↓
Knowledge / Ingestion / RAG / Evaluation Service
          ↓
MyBatis-Plus + LangChain4j + 本地文件存储
          ↓
MySQL       Elasticsearch       模型服务
```

已按以下结构创建工程目录：

```text
knowledge-copilot/
├── doc/
│   ├── 应用开发计划.md
│   └── V1版本开发方案.md
├── server/
│   ├── pom.xml
│   ├── README.md
│   ├── samples/
│   │   ├── documents/
│   │   └── evaluation/
│   └── src/
│       ├── main/
│       │   ├── java/com/example/knowledgecopilot/
│       │   └── resources/
│       │       ├── application.yml
│       │       └── db/migration/
│       └── test/java/com/example/knowledgecopilot/
└── web/
    └── .gitkeep
```

包按业务组织：`knowledge.base`、`knowledge.document`、`knowledge.chunk`、`knowledge.ingestion`、`rag`、`evaluation`、`infrastructure`、`common`。Controller、Service、Mapper、Entity、DTO/VO 放在对应业务包内；公共配置和异常处理集中维护。

业务 Service 默认使用具体类。只有框架契约或确实存在多个实现时才增加接口，例如 Mapper 和 AiServices 声明接口。原计划的 Parser/Splitter 适配层在 V1 使用薄的具体类，不为单一实现建立多层接口。

所有新增 Java 代码遵循阿里巴巴 Java 开发规范；构造器注入、明确常量与枚举、清晰异常语义，避免 Entity 直接作为接口响应。实施前先参考届时模块内已有同类实现。

## 3. 依赖与模型配置

### 3.1 框架复用

| 能力 | 实现方式 |
| --- | --- |
| REST、参数校验 | Spring MVC、Jakarta Validation |
| 接口文档 | Knife4j OpenAPI3 Jakarta Starter |
| 持久化 | MyBatis-Plus Boot 3 Starter、MySQL Driver |
| SQL 迁移 | Flyway，迁移脚本纳入版本管理 |
| 解析 | LangChain4j ApacheTikaDocumentParser |
| 切片 | LangChain4j DocumentSplitters.recursive |
| Embedding | LangChain4j EmbeddingModel 与对应 Provider |
| 向量存储 | LangChain4j ElasticsearchEmbeddingStore |
| 检索 | LangChain4j EmbeddingStoreContentRetriever |
| 答案生成 | LangChain4j AiServices、ChatModel |
| 业务能力 | 本项目实现文档状态、清洗、引用、评测与接口 |

LangChain4j 统一通过 BOM 管理，不逐模块指定版本；允许官方 BOM 对核心和 Integration 使用不同版本号，不手动强行拉齐。

Knife4j 的 Boot 3 接入使用 `knife4j-openapi3-jakarta-spring-boot-starter`，文档入口为 `/doc.html`，OpenAPI JSON 为 `/v3/api-docs`。Starter 已包含 springdoc 依赖，实施时检查依赖树及与 Boot 3.5 的兼容性。[Knife4j 官方快速开始](https://doc.xiaominfo.com/docs/quick-start)

LangChain4j 官方区分 Boot 3 与 Boot 4 Starter，本项目保持 Boot 3 系列。[LangChain4j Spring Boot 集成](https://docs.langchain4j.dev/tutorials/spring-boot-integration/)

具体补丁版本和 Elasticsearch 服务端版本在第一个实施里程碑固定到 POM、部署说明中。通过编译、启动、接口文档访问、向量读写/过滤/删除冒烟验证后锁定；本方案不声称已完成运行兼容性验证。

### 3.2 模型接入边界

对话和 Embedding 分别配置，不要求来自同一服务商。首版默认提供 LangChain4j 的 OpenAI-compatible 接入配置；业务只依赖 ChatModel、EmbeddingModel。若最终服务商不支持该协议，应增加其官方 Integration 及配置 Bean，不能仅修改 base-url 就假设任意 Provider 可用。

| 配置 | 内容 |
| --- | --- |
| Chat | enabled、base-url、api-key、model-name、timeout、max-retries |
| Embedding | enabled、base-url、api-key、model-name、dimension、timeout、max-retries |
| Token 估算 | estimator 标识及配置；与模型不完全一致时明确为估算值 |
| Elasticsearch | 地址、凭据、index-name、连接超时 |
| 文件 | storage-root、max-file-size |
| 入库 | worker-count、queue-capacity、embedding-batch-size |
| RAG | chunk-max-tokens、chunk-overlap-tokens、top-k、min-score、context-max-tokens |
| 评测 | candidate-chunk-limit、worker-count、queue-capacity |

默认切片 500 token、重叠 50 token，问答 topK=5，入库工作线程 2、队列 20，评测工作线程 1、队列 5。候选阈值与上下文预算必须可配置，并在运行记录中保存实际值；不声称不同模型的分数阈值可直接复用。

密钥通过环境变量或本地未提交配置提供。模型默认可禁用，禁用时应用仍可启动并访问 Knife4j、执行普通 CRUD；模型相关接口返回明确的“模型未配置”错误，不能伪造回答或评测结果。入库需要 Embedding，问答需要 Embedding 和 Chat，检索评测只需要 Embedding。

Embedding 启用时校验输出维度与 ES mapping 一致；保存模型标识/配置指纹，更换同维度但不同模型也禁止混用旧索引。更换 Embedding 模型需要显式重建语料索引；V1 不提供在线迁移或已成功文档重索引接口，开发环境可使用新知识库、新索引并重新上传。

## 4. 数据模型

V1 建立 7 张业务表，不提前建立原计划全部 13 张表。ID 使用统一 BIGINT 主键策略，接口以字符串表达以兼容后续前端；业务关联由服务层校验，普通查询明确过滤逻辑删除记录。

| 表 | 主要字段及用途 |
| --- | --- |
| knowledge_base | id、name、description、corpus_revision、is_deleted、时间字段 |
| knowledge_document | id、knowledge_base_id、original_name、storage_path、file_type、file_size、sha256、status、attempt_no、chunk_count、pipeline_config_json、error_code、error_message、时间字段 |
| document_chunk | id、knowledge_base_id、document_id、attempt_no、chunk_index、content、token_count、page、section、embedding_id、时间字段 |
| evaluation_dataset | id、knowledge_base_id、name、description、revision、is_deleted、时间字段 |
| evaluation_case | id、dataset_id、question、expected_answer、relevant_document_ids_json、evidence_json、expected_refusal、tags_json、时间字段 |
| evaluation_run | id、dataset_id、status、case_snapshot_json、config_snapshot_json、corpus_manifest_json、dataset_revision、corpus_revision、metrics_json、各类用例计数、error、开始/结束时间 |
| evaluation_case_result | id、run_id、case_id、case_snapshot_json、status、retrieved_chunks_json、ranked_documents_json、metrics_json、latency_ms、error |

补充约束：

- `document_chunk(document_id, attempt_no, chunk_index)` 唯一，embedding_id 唯一；文档表索引覆盖知识库与状态，评测结果表 `(run_id, case_id)` 唯一。
- page、section 允许为空，不制造页码。evidence_json 保存 `{documentId, text}` 列表，将每段证据绑定到文档。
- JSON 仅用于配置、集合和历史快照；高频筛选字段保留普通列。完整切片正文保存在 MySQL，原始文件保存在本地。
- attempt_no 是失败重试的处理批次，用于隔离残留结果，不具备业务版本发布能力。
- 不建立 document_chunk_set、chat_session、chat_message、rag_trace、user_feedback、bad_case。
- V2 引入 ChunkSet 时，为已有 AVAILABLE 文档迁移生成首个已发布集合，保留 documentId 和现有 chunkId 的关联。
- 原文件、切片和业务记录的写入不是分布式事务，按后文顺序与补偿处理；不能依赖 MySQL 回滚撤销文件或 ES 操作。

## 5. 文档入库与生命周期

### 5.1 上传与解析

1. 校验知识库、文件大小、扩展名和实际内容类型；TXT/Markdown 默认 UTF-8，无法正确解码时明确失败。
2. 使用服务端生成的文件名写入 storage-root 下的临时文件，再移动到正式路径，原始文件名只作为元数据。
3. 保存 UPLOADED 文档记录，事务提交后投递后台任务。DB 保存失败时补偿删除本次文件；异常退出残留文件在维护说明中给出检查清理方法。
4. 上传成功返回 HTTP 202、documentId、status；上传成功只表示已受理，不表示可问答。
5. 后台通过条件更新领取任务，按解析 → 清洗 → 切片 → Embedding → ES 写入执行。外部调用不得放在长数据库事务中。

使用 Tika 提取文本并显式禁用 OCR 路径。加密不可读文件、损坏文件、扫描件无有效文本分别保留明确失败原因；不因为 Tika 能识别更多格式就扩大接口允许列表。

清洗只规范换行、空白和控制字符，保留段落、Markdown 标题与代码缩进。页眉页脚、版权文字仅按显式配置规则删除，不默认猜测并删除重复行。V1 不承诺复杂表格或版面还原。

### 5.2 状态与恢复

```text
UPLOADED → PARSING → PARSED → INDEXING → AVAILABLE
               ↓                  ↓
         PARSE_FAILED        INDEX_FAILED

调度/重启中断 → PROCESS_FAILED
删除 → DELETING → DELETED
                 ↓
             DELETE_FAILED
```

PARSED 表示解析和清洗完成；切片、Embedding、索引阶段错误统一记为 INDEX_FAILED，并通过 error_code 区分阶段。状态接口同时返回当前阶段、切片数量和错误，V1 不提供虚假的百分比进度。

入库失败重试仅允许 PARSE_FAILED、INDEX_FAILED、PROCESS_FAILED。条件更新将状态转为 UPLOADED、attempt_no 加一并清空错误，再投递任务；并发重试仅一条成功，其余返回 409。队列满时将已持久化任务标记 PROCESS_FAILED，记录 TASK_QUEUE_FULL；不能留下无人处理的 UPLOADED。

应用启动、接收请求之前，将上次遗留的 UPLOADED/PARSING/PARSED/INDEXING 标记 PROCESS_FAILED，错误为 PROCESS_INTERRUPTED；遗留 DELETING 标记 DELETE_FAILED，供用户再次删除。该恢复规则只适用于 V1 单实例。

每次重试重新生成本批次切片；对同一批次用确定的 embedding_id 写入，网络重试不得追加重复记录。旧批次索引先清理，失败则本次任务失败，不能带着未知残留继续发布。网络调用配置超时与有限次数重试，不自动无限重跑整个文档。

### 5.3 检索可见性与删除一致性

ES 存储切片正文、向量和 knowledgeBaseId、documentId、attemptNo、chunkId、chunkIndex、tokenCount，以及可选 page/section。使用官方 EmbeddingStore 的读写和 Metadata Filter 能力；索引 refresh/可见性验证可使用 Integration 暴露的官方 ES 客户端，不再封装自研向量框架。[LangChain4j Elasticsearch 集成](https://docs.langchain4j.dev/integrations/embedding-stores/elasticsearch/)

只有全部切片向量写入成功、数量校验通过并确认可搜索后，才将文档条件更新为 AVAILABLE，同时递增 corpus_revision。部分写入、失败和待处理文档不能被问答或评测检索。

V1 为小规模单实例验证采用直接方案：从 MySQL 获取知识库当前 AVAILABLE 文档及其 attempt_no，构造 `knowledgeBaseId AND ((documentId AND attemptNo) OR ...)` 检索前过滤；集合为空时直接返回无结果，禁止退化为无过滤查询。该方案避免在失败索引中过滤后才丢失 TopK，但文档数量增长后需评估过滤表达式规模，后续可随 ChunkSet 发布机制升级。

删除规则：

1. 对处理中状态返回 409；V1 不做任务取消。允许删除成功或失败文档。
2. 事务内置为 DELETING，并递增 corpus_revision，使后续检索不再选择该文档。
3. 删除该文档所有批次 ES 数据、本地原文件和业务切片，再保留最小 DELETED 文档记录。
4. 外部清理失败则标记 DELETE_FAILED，维持不可检索；再次 DELETE 继续幂等清理，文件或向量已不存在视为成功。
5. 重复删除 DELETED 返回成功。知识库内存在未清理文档或未删除评测集时，拒绝删除知识库，不做隐式级联大批删除。

问答在生成前及返回前再次核验引用文档仍可用；并发删除导致状态变化时返回 409，提示重新提问，不返回已经确认失效的引用。评测使用第 7 节的语料修订检测。

## 6. 单轮问答与引用

### 6.1 调用链

```text
knowledgeBaseId + question
 → 校验模型与知识库
 → 获取有效文档/批次过滤条件
 → EmbeddingStoreContentRetriever 检索一次
 → 按上下文预算选取切片
 → 无切片：固定拒答
 → 有切片：AiServices + ChatModel
 → 从本次实际注入的切片构造引用
 → 校验文档可用状态并返回
```

项目用普通 Service 控制这一条业务链路。显式检索后把同一份内容传给 AiServices，避免“先检查是否为空，再由 AiServices 重新检索”产生不同结果；不自研 Pipeline Engine。

Prompt 要求仅依据提供的资料回答，资料不足时说明不足，文档文本作为资料而非系统指令。无候选时通过代码保证拒答；有不相关候选时仅靠 Prompt 不能保证拒答正确，需在无答案用例中人工核验，不将其描述为已实现语义充分性判定。

V1 不使用 ChatMemory，不将上次请求或跨请求可变数据放入共享模型对象。问题长度、检索 topK、上下文 token 预算设配置上限；预算裁剪后引用必须对应真正发送给模型的切片。

### 6.2 接口数据

请求示例：

```json
{
  "knowledgeBaseId": "1001",
  "question": "设备在购买后多久可以申请退货？"
}
```

成功 data 示例：

```json
{
  "answer": "根据售后政策，满足规定条件时可在购买后 7 天内申请退货。",
  "refused": false,
  "citations": [
    {
      "documentId": "2001",
      "documentName": "示例售后政策.md",
      "chunkId": "3001",
      "content": "在购买后 7 天内，满足本政策所列条件的设备可以申请退货。",
      "page": null,
      "section": null
    }
  ]
}
```

以上业务内容仅为接口结构示意，以后续示例资料实际内容为准。

citations 表示“本次回答使用的检索上下文来源”，不宣称逐句支持或已自动验证答案。所有引用 ID、名称及正文均来自保存的 Chunk Metadata 和本次上下文，不让模型生成。需要核验完整片段时使用切片详情接口。

无检索结果返回 `refused=true`、空 citations、固定答案“当前知识库没有足够的信息回答该问题。”；模型超时、ES 失败和模型未配置返回错误，不能伪装成正常拒答。若模型在有上下文时输出规定的固定拒答，规范化 refused 字段；V1 不用另一次模型调用判定拒答。

## 7. Evaluation Lite

### 7.1 数据集与用例

每个 Dataset 绑定一个知识库。正向用例需要非空 relevantDocumentIds；文档必须属于该知识库，运行时必须 AVAILABLE。expectedAnswer、证据原文用于人工核验，不自动调用 LLM Judge。证据应标注到相应 documentId，不永久绑定 chunkId。

无答案用例使用 expectedRefusal=true、空 relevantDocumentIds。与正向检索指标分开统计，不将空相关文档集合算成满分，也不参与分母。

### 7.2 文档排名与指标口径

评测复用问答的检索实现、过滤规则、Embedding 模型与 min-score，仅扩大候选切片数量。默认检索最多 100 个候选切片，按返回顺序保留每个文档首次出现的位置，得到去重后的文档排名，再截取前 10 个文档。

K 在本方案中指去重后的文档数，不是切片数。少于 K 个文档时按实际结果计算，不补齐、不重复计数；超过候选窗口的文档视为本次未召回。该指标衡量固定候选窗口下的文档检索能力，并不等同于线上 topK=5 切片所提供的上下文质量。运行保存 candidateChunkLimit，改变窗口后需重新建立可比基线。

对每个正向用例，相关文档集合为 R，前 K 个去重文档为 D_K：

- Recall@K = |R ∩ D_K| / |R|，分别计算 K=5、10。
- RR@10 = 第一个相关文档在去重前 10 名中的排名倒数；没有命中为 0。
- MRR@10 = 所有正向用例 RR@10 的算术平均。
- Hit Rate@10 = 前 10 名至少命中一个相关文档的正向用例比例。
- Recall 使用逐用例算术平均；未命中的正常执行用例记 0，服务异常的用例记 ERROR，不当作普通未命中。

指标单元测试使用固定排名验证，例如相关集合 {A,C}，候选切片属于 {B,B,A,C}，去重后排名 {B,A,C}：Recall@5=1、RR@10=1/2、Hit@10=1。另覆盖空检索、多相关文档、重复切片及排名超过 10。

### 7.3 执行与快照

1. 触发时验证至少一个正向用例、引用文档有效、模型可用，保存用例快照、数据集修订号、语料清单和配置快照，再异步返回 runId。
2. 语料清单包含 AVAILABLE 文档 ID、文件 hash、attempt_no 与切片配置；配置包含索引、Embedding 模型指纹、token 估算器、阈值、候选窗口和指标口径版本，不保存密钥。
3. 逐用例检索，保存原始候选切片 ID/文档 ID/正文快照及可获得的分数、去重文档排名、耗时、指标或错误。框架不暴露分数时字段为空，不能捏造分数。
4. 无答案用例仅保存检索结果，状态标记 MANUAL_REVIEW，不自动生成答案。通过 Chat API 单独提问，按检查清单人工记录拒答是否合理。
5. 运行开始与结束检查 corpus_revision；期间语料可用集合变化则该运行标记 FAILED/CORPUS_CHANGED，保留明细，禁止作为有效基线。数据集后续修改不影响已保存的用例快照。
6. 状态为 QUEUED/RUNNING/COMPLETED/FAILED。任一正向用例发生执行错误则整个运行 FAILED；可保留部分统计供排查，但不输出有效基线总分。
7. 队列满时将已保存运行标记 FAILED；启动时将遗留 QUEUED/RUNNING 标记 FAILED/PROCESS_INTERRUPTED。重跑生成新的 runId，不覆盖旧结果。

历史运行只读保留。数据集逻辑删除不连带删除历史快照；正在运行的数据集拒绝删除。模型或语料变化后不能仅以 Dataset 名称相同就认为两次运行完全可比。

### 7.4 示例基线

实施交付默认 5 份自编中文资料，覆盖产品说明、售后政策、FAQ、内部制度、操作规范；准备 PDF、DOC、DOCX、TXT、Markdown 格式样本，验证五类格式能提取有效正文。

建立 `rag-baseline-v1`，至少 20 条用例：12 条单文档相关、4 条多文档相关、4 条无答案。另准备扫描 PDF、损坏文件等失败验证材料，不混入正向语料。

示例评测包使用稳定的 documentKey 标识文档，不写死数据库 ID；导入请求提交 documentKey → documentId 映射。校验所有映射属于目标知识库后，一次事务导入 Dataset/Case，映射缺失则整体失败，避免产生错误 Ground Truth。

示例资料只验证流程和计算口径，运行后记录实际指标，不伪造预期召回率或作为真实业务效果承诺。

## 8. API 清单与 Knife4j 验收入口

统一前缀 `/api/v1`。常规 JSON 响应采用 `{code, message, data, requestId}`，配合准确的 HTTP 状态码；分页采用 pageNo/pageSize，默认 20、上限 100。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST / GET | /knowledge-bases | 创建、分页查询知识库 |
| GET / PUT / DELETE | /knowledge-bases/{id} | 详情、修改名称描述、删除空知识库 |
| POST | /knowledge-bases/{id}/documents | multipart 单文件上传，返回 202 |
| GET | /knowledge-bases/{id}/documents | 文档分页列表，支持状态筛选 |
| GET | /documents/{id} | 文档元数据和当前状态 |
| GET | /documents/{id}/status | 处理阶段、失败原因和切片数量 |
| POST | /documents/{id}/retry | 入库失败重试，返回 202 |
| DELETE | /documents/{id} | 删除或重试清理；成功后不可检索 |
| GET | /documents/{id}/chunks | 当前批次切片分页查看 |
| GET | /chunks/{id} | 正文及 Metadata |
| POST | /chat | 单轮同步问答 |
| POST / GET | /evaluation/datasets | 创建、分页查询数据集 |
| GET / PUT / DELETE | /evaluation/datasets/{id} | 数据集详情、修改、逻辑删除 |
| POST / GET | /evaluation/datasets/{id}/cases | 新建、分页查询用例 |
| GET / PUT / DELETE | /evaluation/cases/{id} | 查看、修改、删除用例 |
| POST | /evaluation/datasets/import | JSON 评测包及文档映射，一次导入 |
| POST | /evaluation/datasets/{id}/runs | 异步触发检索评测，返回 202 |
| GET | /evaluation/datasets/{id}/runs | 历史运行列表 |
| GET | /evaluation/runs/{id} | 状态、配置与指标 |
| GET | /evaluation/runs/{id}/results | 分页查询用例明细和快照 |

错误至少覆盖：400 参数/评测映射错误、404 资源不存在、409 状态冲突、413 文件过大、415 格式不支持、503 模型未配置/依赖不可用、504 外部模型超时。异步任务失败通过状态接口返回，不把 HTTP 202 解释为任务成功。

Knife4j 按知识库、文档、问答、评测分组；每个接口有中文说明、字段约束、请求/响应示例和状态语义。文件接口能选择文件上传，JSON 导入接口提供可复制示例，无 Authorization 配置。

## 10. 测试与验收清单

### 10.1 必要自动化检查

- 指标测试：去重、Recall 分母、MRR 排名、空结果、多相关文档、无答案排除、执行错误不冒充低分。
- 生命周期测试：并发领取/重试、队列拒绝、重启恢复、部分索引失败和删除失败的状态转换。
- 集成测试：真实 MySQL/ES 环境下，Metadata Filter、指定 ID 幂等写入、可见性与删除有效；不要求普通单元测试调用收费模型。
- RAG 测试：空检索不调用 Chat、跨知识库过滤、引用来源和上下文裁剪一致、外部错误不转成拒答。
- 真实模型端到端验收由用户配置模型后执行；模型未配置时只能完成不依赖它的检查，不能标记全部验收通过。

### 10.2 Knife4j 人工验收顺序

1. 按 README 配置 MySQL、ES、本地文件路径及模型，启动后端，打开 `/doc.html`。
2. 创建知识库 A/B，各上传一份内容不同的文档；轮询直到 AVAILABLE，查看切片正文。
3. 在 A 提问并核验答案、documentId、chunkId、引用原文；确认不能检索 B 的文档。
4. 在空知识库提问，确认固定拒答；对有语料但无答案的问题，人工核验模型是否正确说明资料不足。
5. 上传扫描件/损坏文件/超限文件，核验同步拒绝或异步失败原因。
6. 制造一次 Embedding/ES 失败，恢复依赖并重试，确认未出现重复有效切片或半成品检索。
7. 处理过程中重启服务，确认遗留任务失败、允许重试；同一文档并发重试只受理一次。
8. 删除文档后确认后续问答不再引用；模拟清理失败，再次 DELETE 可完成清理。
9. 上传示例语料，以返回 ID 构造映射导入基线，触发运行并查询四项指标和逐条明细。
10. 修改评测集后重跑，确认旧运行快照保留；运行期间改变语料，确认标记 CORPUS_CHANGED。
11. 通过 Chat API 核验无答案用例，在验收记录中保存问题、实际答案与人工结论。

### 10.3 实施交付物

- `server/` 中可构建运行的后端、数据库迁移脚本和必要测试。
- `web/.gitkeep`，不包含前端业务实现。
