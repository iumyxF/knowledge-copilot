# Knowledge Copilot 企业知识库智能助手

## Java 应用开发计划（优化版）

---

# 1. 项目定位

Knowledge Copilot 是一套基于：

```text
Java 21
Spring Boot
LangChain4j
Elasticsearch
MySQL
Mybatis-Plus
```

开发的企业内部知识库智能助手。

主要用于管理和检索：

```text
产品手册
技术文档
售后政策
FAQ
公司制度
操作规范
Markdown
PDF
Word
TXT
```

等企业内部知识。

项目核心目标不是重新开发一套 RAG Framework，而是：

> 基于 LangChain4j 已有能力，开发企业真正需要的知识治理、RAG 质量管理、评测反馈和 Agent 应用能力。

---

# 2. 核心开发原则

## 2.1 优先复用 LangChain4j

统一遵循：

```text
LangChain4j 已经实现
→ 直接使用

LangChain4j 已提供统一接口
→ 实现 / 适配其接口

企业知识库业务能力
→ 项目实现

LangChain4j 没有对应能力
→ 再考虑第三方框架或自行实现
```

例如：

```text
PDF / Word 解析
→ LangChain4j DocumentParser

Chunk
→ DocumentSplitters.recursive()

Embedding
→ EmbeddingModel

Vector Store
→ ElasticsearchEmbeddingStore

Advanced RAG
→ DefaultRetrievalAugmentor

RRF
→ DefaultContentAggregator

Reranker
→ ReRankingContentAggregator + ScoringModel

ChatMemory
→ LangChain4j ChatMemory

Tool Calling
→ @Tool

MCP
→ McpClient
```

# 3. 开发原则

整个项目保持以下原则。

## 3.1 模块化单体优先

第一阶段：

```text

```

暂时不引入：

```text

Redis

```

避免把时间消耗在基础设施建设上。

## 3.2 业务流程自己掌握

```text

Embedding
Document Parser
Document Splitter
Vector Store Integration
RAG Components

Feedback

```

---

## 3.3 任何优化必须可以评测

不采用：

```text
“感觉效果更好”
```

作为技术升级依据。

例如：

```text
500 Token → 300 Token
Vector → Hybrid
增加 Query Rewrite
增加 Reranker

```

都应该通过 Evaluation Dataset 验证。

因此：

> Evaluation 不再等到项目后期才开发。

从 V1 开始建立最小评测能力。

# 15. Citation 设计原则

这是原计划需要重点修正的地方。

Citation 不应该假设任何 Parser 都一定可以返回：

```text
page
section
```

所以基础 Citation 定义为：

```text
documentId      必须
documentName    必须
chunkId         必须

page            可选
section         可选
```

例如：

```json
{
  "documentId": 1001,
  "documentName": "GX-3000.pdf",
  "chunkId": "chunk-xxx",
  "page": 18,
  "section": "故障处理"
}
```

如果 Parser 没有可靠页码：

```json
{
  "documentId": 1001,
  "documentName": "GX-3000.pdf",
  "chunkId": "chunk-xxx"
}
```

不要：

```text
让 LLM 自己生成 Citation
```

Citation 必须来源于：

```text
TextSegment.metadata()
```

以及 Knowledge Copilot 自己保存的 Chunk Metadata。

# 21. ChunkSet 不可变发布原则

非常重要：

> PUBLISHED ChunkSet 永远不原地修改。

人工调整时：

```text
Published V1
     ↓
Copy
     ↓
Draft V2
     ↓
Split / Merge
     ↓
Embedding
     ↓
Index
     ↓
Evaluation
     ↓
Publish V2
```

只有 V2：

```text
Embedding 完成
Index 完成
Evaluation 通过
```

以后才切换：

```text
publishedChunkSetId
V1 → V2
```

Retriever 始终添加：

```text
chunkSetId = 当前发布版本
```

Metadata Filter。

---

# 22. ChunkSet 发布失败处理

例如：

```text
V2 Embedding 失败
```

则：

```text
V1 继续服务
V2 保持 DRAFT / FAILED
```

不会影响线上知识查询。

禁止：

```text
先 delete V1
再生成 V2
```

这样的破坏式更新。

# 33. 不把 relevantChunkId 作为永久 Ground Truth

原因：

```text
ChunkSet A
500 / 50

ChunkSet B
300 / 30
```

重新切片以后：

```text

```

会发生变化。

因此 Ground Truth 应优先描述：

```text
Document
+
Evidence
```

例如：

```text
documentId
evidenceText
```

如果解析质量足够稳定，也可以：

```text
documentId
page
section
evidenceText
```

`relevantChunkIds` 可以作为：

```text

```

产生的派生数据，而不是 Dataset 永久定义。

# 69. Agentic Loop

Java 控制：

```java
for (int i = 0; i < maxRetry; i++) {

    var contents = retrieve(query);

    var evaluation =
        retrievalJudge.judge(query, contents);

    if (evaluation.sufficient()) {
        break;
    }

    query = rewrite(
        query,
        evaluation.reason()
    );
}
```

默认：

```text
maxRetry = 2
```
